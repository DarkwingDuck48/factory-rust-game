# Данные (data/)

## Описательный механизм цепочек (data-driven рецепты)

- Цепочки/рецепты описываются **данными**, а не зашиваются в логику
  игры: рецепт = набор входов → выход (+ стоимость, время производства,
  требуемое здание / роль города).
- **Тир продукта вычисляется автоматически** по правилу
  «макс(тиры входов) + 1»; для добывающих рецептов тир задаётся
  исследованием в дереве технологий.
- У ресурса может быть несколько рецептов разных тиров (например,
  уголь: Т1 из дерева и Т2 из шахты).
- Логика игры работает с **общим механизмом «рецепт: вход → выход»**
  и не знает, какие именно цепочки существуют.
- Новая цепочка добавляется **без изменения основной логики**:
  правкой описания (данные/конфигурация), а не кода.
- Это позволит быстро прототипировать и балансировать цепочки
  в процессе разработки.

## Общие принципы

Данные игры (ресурсы, здания, роли городов, рецепты, переводы) лежат
**открыто в папке `data/`** рядом с исполняемым файлом; моддеры правят
и дополняют их напрямую. Эта папка — рабочая, у игрока; её исходная
версия хранится в репозитории (`./assets/data/`) и раскладывается при
первом запуске.

### Терминология

- `assets` — неизменяемые данные игры (источник, в репозитории),
- `data` — рабочая папка игрока.

### Хранение и доставка начальных данных

- **Источник (репозиторий):** `./assets/data/` в корне воркспейса —
  те же файлы, что и в игре; версионируются в git, балансные правки
  видны в диффах. Это же **тестовая фикстура**: загрузчик
  `factory-core` читает репо-`assets/data/` в юнит-тестах
  (валидация + сверка тиров и ссылок) — поломка формата ловится
  без запуска игры.
- **Доставка:** дефолтный набор встраивается в бинарь
  (встроенные строки / `include_dir`). При первом запуске, если папки
  `data/` рядом с exe нет, игра раскладывает её (`factory-edit init`
  делает то же самое).
- **Правило неразрушаемости:** материализация и `init` **никогда не
  перезаписывают** существующие файлы — только создают недостающие.
  Иначе обновление игры затрёт правки игрока и моды.
- После материализации папка `data/` игрока — **единственный источник
  правды**; репо-`assets/data/` на игровой процесс больше не влияет.

### Структура папки

Рабочая папка игрока:

```
data/
├── resources.toml        # каталог всех ресурсов (Т0 и производных)
├── buildings.toml        # каталог зданий
├── cities.toml           # роли городов-производителей + их рецепты
├── lang/
│   └── ru.toml           # файл перевода (по файлу на язык)
└── recipes/
    ├── extraction.toml   # добыча: без входов, тир явный
    └── production.toml   # переработка: тир вычисляется
```

### Общие правила

- **`id` — технический**: на него ссылаются рецепты, здания и роли.
  Менять напрямую нельзя (сломаются ссылки) — только через
  `factory-edit rename`.
- **`code` — публичный**: ключ локализации. По умолчанию вычисляется
  из id (`resource.<id>`, `building.<id>`, `role.<id>`); поле `code`
  позволяет переопределить ключ. «Переименовать» в интерфейсе — правка
  `lang/`, ссылки не трогаются.
- **Строки-имена в данных не хранятся** — только коды. Нет перевода →
  интерфейс показывает сырой код (`resource.wood`); валидатор выдаёт
  предупреждение, но не блокирует игру.
- **Категория — тоже код**: `category = "material"` переводится
  в секции `[category]`.
- Дубликат `code` среди сущностей одного типа — ошибка валидации.
- **Тир производного рецепта вычисляется**: `макс(тиры входов) + 1`.
  У добывающих — тир явный: `tier = 0` (доступно со старта) или
  `tier = 2` + `research` (открывается исследованием).
- У ресурса может быть несколько рецептов **разных тиров** (уголь:
  Т1 из дерева и Т2 из шахты).
- `time` — секунды реального времени (float).

## `resources.toml` — каталог ресурсов

```toml
[wood]                  # id технический; code по умолчанию = resource.wood
category = "material"   # material | metal | component | premium
icon = "W"              # символ для TUI
# base_price = 2        # зарезервировано (экономика уточняется)

[stone]
category = "material"

[sand]
category = "material"

[coal]
category = "material"

[quartz]
category = "component"

[iron]
category = "metal"

[copper]
category = "metal"

[lithium]
category = "metal"

[battery]
category = "component"

[chip]
category = "component"

[glass]
category = "component"

[ev]
category = "premium"
```

Тир в каталоге **не хранится**: для производных он вычисляется из
рецептов, Т0 — это ресурсы без входящих рецептов (добыча `tier = 0`).

## `buildings.toml` — каталог зданий

```toml
[sawmill]               # code по умолчанию = building.sawmill
category = "extraction"

[quarry]
category = "extraction"

[sand_quarry]
category = "extraction"

[coal_plant]
category = "production"

[mine]
category = "extraction"

[iron_mine]
category = "extraction"

[copper_mine]
category = "extraction"

[lithium_mine]
category = "extraction"

[factory]
category = "production"
```

## `recipes/extraction.toml` — добыча

Без `inputs`; `tier` обязателен; `research` — ссылка на узел дерева
технологий (файл дерева появится позже).

```toml
[extract_wood]
building = "sawmill"
time = 3.0
tier = 0
outputs = { wood = 1 }

[extract_stone]
building = "quarry"
time = 3.0
tier = 0
outputs = { stone = 1 }

[extract_sand]
building = "sand_quarry"
time = 3.0
tier = 0
outputs = { sand = 1 }

[extract_coal]          # тот же уголь, но Т2 — из шахты
building = "mine"
time = 5.0
tier = 2
research = "coal_mining"
outputs = { coal = 1 }

[extract_iron]
building = "iron_mine"
time = 5.0
tier = 2
research = "iron_mining"
outputs = { iron = 1 }

[extract_copper]
building = "copper_mine"
time = 5.0
tier = 2
research = "copper_mining"
outputs = { copper = 1 }

[extract_lithium]
building = "lithium_mine"
time = 5.0
tier = 2
research = "lithium_mining"
outputs = { lithium = 1 }
```

## `recipes/production.toml` — переработка

`inputs` — именованная таблица (`ключ = id ресурса`): дубликат входа
невозможен (запрещает сам парсер TOML). `tier` не указывается.

```toml
[coal_from_wood]        # coal: макс(0) + 1 = Т1
building = "coal_plant"
time = 5.0
inputs  = { wood = 2 }
outputs = { coal = 1 }

[quartz_from_sand]      # quartz: Т1
building = "factory"
time = 4.0
inputs  = { sand = 2 }
outputs = { quartz = 1 }

[chip_from_quartz]      # chip: макс(Т1, Т2) + 1 = Т3
building = "factory"
time = 8.0
inputs  = { quartz = 1, copper = 1 }
outputs = { chip = 1 }

[ev_from_parts]         # ev: макс(Т3, ...) + 1 = Т4
building = "factory"
time = 20.0
inputs  = { battery = 1, iron = 1, copper = 1 }
outputs = { ev = 1 }
```

Наименование рецепта в интерфейсе **не переводится отдельно** —
собирается из названий ресурсов («2 Дерево → 1 Уголь»).

## `cities.toml` — роли городов

Город-производитель имеет **один** рецепт — вложенная таблица
`[<роль>.recipe]`.

```toml
[battery_producer]      # code по умолчанию = role.battery_producer
icon = "B"

[battery_producer.recipe]
time = 10.0
inputs  = { lithium = 1 }
outputs = { battery = 1 }

[chip_producer]
icon = "C"

[chip_producer.recipe]
time = 10.0
inputs  = { quartz = 1, copper = 1 }
outputs = { chip = 1 }

[glass_producer]
icon = "G"

[glass_producer.recipe]
time = 10.0
inputs  = { sand = 2, coal = 1 }
outputs = { glass = 1 }
```

## Мерж и переопределение

- Рецепты: читаются **все** `*.toml` из `recipes/` в алфавитном порядке;
  файл, идущий позже, переопределяет id, заявленный раньше. Мод добавляет
  свой `recipes/zz_mymod.toml`, не трогая базовые файлы
  (`inputs`/`outputs` при этом переопределяются целиком).
- Каталоги и переводы — один файл на сущность/язык, правятся напрямую.

## Валидация (в `factory-core`)

Загрузка читает каталоги и рецепты и выдаёт **отчёт со всеми ошибками
сразу** (не останавливаясь на первой), каждая с `file:line`:

- неизвестный id в `inputs`/`outputs`, `building`, `research` + подсказка
  **`did you mean`** (нечёткое сравнение по каталогу);
- ресурс без способа производства / рецепт с несуществующим выходом;
- дубликаты id и `code` между файлами;
- циклы в графе производств;
- нарушение правила тиров; добывающий рецепт без `tier`;
- отсутствие перевода в активном языке — предупреждение (не блокирует);
- на этапе разработки — строгая схема полей (`deny_unknown_fields`):
  опечатки в именах полей ловятся сразу. Перед релизом решить:
  версионировать схему или перейти на «неизвестное поле = предупреждение».

Отчёт показывается в TUI **при старте игры** (невалидные данные = игра
не запускается) и в CLI через `factory-edit validate`.

## `factory-edit` — CLI для работы с данными

Отдельный крейт-бинарь: генератор и редактор, в котором id/коды не
печатаются руками — всё выбирается/подставляется автоматически:

- `new resource | building | role | recipe` — визарды: выбор из
  каталогов вместо ввода, автогенерация `code`, дописывание перевода
  в `lang/<активный язык>.toml`;
- `rename <id> <новый>` — рефакторинг ссылок во всех файлах данных;
- `rename-code <старый> <новый>` — переименование ключа локализации
  во всех языковых файлах;
- `show <id>` — ресурс, его рецепты, цепочки вверх/вниз;
- `validate` — проверка данных (тот же валидатор, что в игре);
- `init` — раскладывает встроенный дефолтный набор `data/`, если его
  нет (существующие файлы не перезаписывает).

Логика визардов и генерации — в `factory-core` (переиспользуется затем
в in-game редакторе), CLI — тонкая обёртка. Запись TOML — через API
`toml_edit` (сохраняет комментарии и порядок таблиц при правках).
